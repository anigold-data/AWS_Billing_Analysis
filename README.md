# AWS Billing Analysis

A Power BI semantic model and report demonstrating enterprise BI engineering practice: a star schema, a documented DAX measure library, row- and object-level security, VertiPaq/DAX Studio performance tuning, and a CI/CD pipeline that validates every change before it reaches `main`.

---

## 1. Project Overview

AWS Billing Analysis simulates a multi-account AWS cost management platform. It comprises a synthetic Cost & Usage Report (CUR) dataset, modeled into a star schema, secured by business unit, tuned for performance, and validated through an automated GitHub Actions pipeline.

The dataset is entirely synthetic. It mirrors the shape of a real AWS CUR export but contains no real AWS billing data and should be treated as fictitious.

## 4. Data Model

A star schema built from the synthetic CUR dataset, using surrogate integer keys throughout:

- **FactsCost** — one row per resource/usage-type/day, housing usage_quantity, unit_rate, unblended_cost, amortized_cost
- **DimDate, DimAccount, DimService, DimRegion, DimResource, DimPricingModel, DimUsage, DimTeam, DimProject, DimEnvironment**

Full ERD: [`docs/erd.png`](docs/erd.png). Full column-by-column and measure-by-measure documentation: [`docs/data_dictionary.md`](docs/data_dictionary.md).

---

## 5. Measures

Organized into a `_Measures` display folder, grouped by category:

- **Core** — Total Cost, Total Amortized Cost, Total Usage, Cost per Unit, Distinct Resources
- **Time Intelligence** — MTD/QTD/YTD Cost, MoM Cost Change %, YoY Cost Change %, Rolling 3-Month Avg Cost, Rolling 7-Day Avg Cost
- **Variance** — Cost Variance vs Prior Month, Cost Variance %, Daily Cost StdDev
- **FinOps KPIs** — On-Demand Cost, Committed Cost, Committed Spend Ratio, Effective Savings Rate, Cost Contribution %

Full descriptions: [`docs/data_dictionary.md`](docs/data_dictionary.md).

## 7. Security

**Row-Level Security** — six roles restrict visibility by `DimAccount[business_unit]`: Engineering, DataPlatform, Marketing, SharedServices see only their own business unit's accounts; Finance and Executive see all accounts (Finance is intentionally unrestricted at the row level, since chargeback/cost-allocation reporting requires cross-BU visibility. See rationale in the security matrix). All roles were created and tested via "View As Role."

**Object-Level Security** — applied in Tabular Editor, restricting two columns to Finance/Executive only: `amortized_cost` and `linked_account_id`. Both are confirmed working.

Full role-by-role and column-by-column detail: [`docs/security-matrix.md`](docs/security-matrix.md).

## 8. Best Practice Analyzer

A full BPA pass was run in Tabular Editor 3 using the built-in Best Practice Analyzer, covering Governance, Performance, Maintenance, and Formatting categories. Fixes applied include: compatibility-level update, `IsAvailableInMdx` disabled on high-cardinality non-slicing columns, summarization disabled on surrogate keys and geographic coordinates, descriptions added to all visible measures and tables, foreign keys hidden, and format strings applied to all cost and ratio measures.

Full findings and fixes: [`docs/bpa-findings.md`](docs/bpa-findings.md).

The same ruleset (`scripts/BPARules.json`) also runs automatically in CI on every pull request via the Tabular Editor CLI, disallowing any future regression against these same standards.

## 9. Performance Tuning

DAX Studio and VertiPaq Analyzer were used to audit the model (~850,619 rows in FactsCost). High-cardinality numeric columns were rounded to 2 decimal places, producing measurable improvements:

| Column | Cardinality Reduction | Storage Size Reduction |
|---|---:|---:|
| `unit_rate` | 99.90% | 94.35% |
| `amortized_cost` | 87.28% | 64.64% |
| `unblended_cost` | 87.21% | 64.63% |
| `usage_quantity` | 33.46% | 18.10% |

DAX Studio Server Timings confirmed all three tested report queries (Monthly Cost Trend, Committed Spend Ratio, Service × Region Matrix) completed in 4–10 ms, with no Formula Engine or Storage Engine bottleneck identified. Optimisation was applied only where needed; columns and expressions already performing efficiently were left unchanged.

Full detail: [`docs/dax_performance_notes.md`](docs/dax_performance_notes.md).

## 10. CI/CD Pipeline

**CI** (`ci.yml`, runs on every pull request):
Downloads the Tabular Editor CLI and runs the Best Practice Analyzer against `scripts/BPARules.json`. Any Error-severity violation fails the check and blocks the merge.

**CD** (`cd.yml`, runs on merge to `main`):
Exports the model's full metadata (tables, columns, measures, relationships) via the Tabular Editor CLI and commits it to `docs/model-metadata.json` automatically.

**Known constraint:** this project was built without Power BI Pro/PPU workspace access, so CD exports documentation rather than deploying to a live workspace.
